# Architecture backend (hôte C#)

L'hôte est une application C# .NET 10 avec une fenêtre WinUI 3 (Windows App SDK, non empaquetée) qui héberge une seule WebView2. Il ne porte aucune interface métier : il gère la fenêtre, les terminaux, la persistance et les services locaux. L'interface entière est dans `web/`.

## Projets

| Projet | Rôle |
| --- | --- |
| `src/Dock.Core` | Bibliothèque sans interface, testable : pseudo-consoles, Job Objects, intégration shell, modèle et persistance de session. Aucune dépendance WinUI. |
| `src/Dock.Host` | Fenêtre WinUI 3, WebView2, pont hôte / web. Contient le moins de logique possible. |
| `tests/Dock.Core.Tests` | Tests xUnit de `Dock.Core` (voir `docs/TESTING.md`). |

`Directory.Build.props` à la racine fixe `Nullable`, `ImplicitUsings`, la plateforme x64 et `win-x64`.

## Dock.Core

| Dossier | Contenu |
| --- | --- |

| `Settings/` | `SettingsModel` (vue d'ensemble des quatre fichiers de réglages : chemins des shells, commande d'éditeur, persistance, racine des projets), `SettingsService` (`Load` agrège les dépôts, `Validate` refuse un shell inconnu, un éditeur vide ou une racine vide / relative, `Save` normalise puis écrit les quatre fichiers, `Snapshot` renvoie pour l'écran d'administration les shells avec chemin par défaut, chemin configuré et disponibilité, les chemins des fichiers et des avertissements non bloquants : shell, éditeur absolu ou racine introuvables). Les fichiers restent éditables à la main : l'écran n'est qu'une autre façon d'écrire les mêmes fichiers. `Export` écrit un `PreferencesDocumentModel` (`version` 1, `shells`, `editor`, `persistence`, `projectsRoot`) dans le fichier choisi ; `Import` lit un tel fichier et le valide intégralement (JSON lisible, version 1 exacte, quatre clés présentes, mêmes règles que `Validate`, persistance bornée) sans rien écrire : il renvoie les réglages ou un message d'erreur en français. Préférences, session (`session.json`) et historique (`text.json`) restent trois fichiers distincts ; l'export ne contient jamais la disposition ni le texte des terminaux. |
| `Agents/` | États des agents rattachés aux panes. `AgentState` (`Working`, `Waiting`, `Done`, `Error`, `Unknown`, sérialisé en camelCase), `PaneAgentModel(PaneId, Agent, State, Message)`, `PaneProbeModel(PaneId, StartedAtUtc, Processes)` (ce que l'hôte sait d'un pane vivant : instant de lancement du shell et noms des processus encore actifs dans son Job Object). `AgentStateRepository` lit `%LOCALAPPDATA%\Dock\agents\<paneId>.json` (`{ agent, state, message? }`, écrit par un producteur externe comme les hooks Claude Code) en ignorant tout fichier plus ancien que le shell du pane, illisible ou d'état inconnu ; `Delete` et `Clear` purgent ces fichiers. `IAgentAdapter` (`Id`, `Name`, `Detect(probe, reported)`) : `ClaudeCodeAdapter` reprend l'état rapporté pour `claude`, sinon « Inconnu » si un processus `claude` tourne ; `CodexAdapter` ne connaît aucun producteur et rapporte « Inconnu » dès qu'un processus `codex` tourne. `AgentMonitor.Resolve(probes)` applique les adaptateurs dans l'ordre et supprime l'état d'un pane dont le shell n'a plus aucun processus enfant (l'agent est parti sans prévenir). La simple présence d'un processus ne produit jamais autre chose que « Inconnu ». |
| `Agents/` (suite) | `NotificationSettingsRepository` (`notifications.json` : `windowsToast` true, `sound` parmi `none`, `Notification.Default`, `Notification.IM`, `Notification.Mail`, `Notification.Reminder`, `Notification.SMS` ou le chemin absolu d'un fichier `.wav`, `taskbarFlash` true ; gabarit écrit si absent, son inconnu ramené au son par défaut, fichier `.wav` introuvable signalé en avertissement non bloquant par `Snapshot`). Cinquième fichier de réglages, présent dans `SettingsModel`, l'export et l'import (clé optionnelle : défauts si absente). |
| `Session/` | Modèles `SessionModel`, `WorkspaceModel`, `TabModel`, `SplitNodeModel`, `PaneModel`, `ClosedTabModel` (onglet fermé restaurable : workspace d'origine, position, onglet et texte sérialisé par pane) ; `SessionValidator` (limites de profondeur, ratios, identifiants actifs, session sans workspace acceptée si `Active` est vide, liste des onglets fermés tronquée aux cinq plus récents, `Favorites` : identifiants de commandes de la palette, au plus 50, non vides, dédoublonnés) ; `SessionRepository` (lecture / écriture atomique de `%LOCALAPPDATA%\Dock\session.json` via un `.tmp` puis renommage, refus d'une session invalide ; un fichier illisible ou invalide est mis en quarantaine et signalé, jamais écrasé en silence) ; `PaneTextRepository` (`text.json`, texte sérialisé par pane des terminaux vivants, écrit à part de la disposition, écriture atomique, panes ignorés au-delà de la limite globale, fichier illisible mis en quarantaine) ; `PersistenceSettingsRepository` (`persistence.json` : `textIntervalSeconds` 30, `linesPerPane` 10 000, `maxTextMebibytes` 256, gabarit écrit si absent, valeurs bornées) ; `CorruptedFiles` (renomme un fichier fautif en `nom.corrompu-AAAAMMJJ-HHmmss.ext` et renvoie ce chemin) ; `AtomicFile` (écriture via `.tmp` puis renommage, utilisée par tous les dépôts) ; `SessionFactory` (session initiale, identifiants). |

Règles :

- L'hôte est la source de vérité de la session persistée : le web envoie la session complète, l'hôte la valide avant d'écrire. Chaque `session.save` ou `text.save` répond `session.saved`, ou `session.saveFailed {message}` (session refusée, disque ou droits) sans faire tomber la session en cours.
- Au démarrage, `app.hello` porte `recovery` quand `session.json` ou `text.json` a été mis en quarantaine ; la session de secours est alors la session initiale et le fichier fautif reste à côté pour récupération.
- Le texte restauré n'est qu'un affichage : les shells sont toujours relancés neufs, aucune commande n'est rejouée.
- `settings.export` ouvre un sélecteur d'enregistrement (`.json`, nom proposé `dock-preferences`) et écrit la configuration enregistrée ; `settings.import` ouvre un sélecteur de fichier `.json`, valide le contenu et renvoie `settings.imported` sans écrire : l'application effective passe par `settings.save`, ce qui vaut confirmation et remplace la configuration (aucune fusion). Un fichier refusé remonte en `error`.
- `settings.save` valide, écrit les quatre fichiers puis applique immédiatement : nouveaux chemins de shells pour les prochains `terminal.create` (les shells déjà lancés ne bougent pas), nouvelle commande d'éditeur, nouvelle racine des projets, nouvelle limite d'historique. Un réglage refusé remonte en `error` sans rien écrire.
- Chaque pane est rattaché à un Job Object avec `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` : fermer un pane (`terminal.close`), un onglet, un workspace ou l'application termine de force tout son arbre de processus, y compris les enfants détachés du shell. Aucun service persistant ne reprend les anciens agents ou serveurs.
- Avant une fermeture, le web demande `terminal.activity {panes}` ; l'hôte répond `terminal.activityResult` avec les panes qui ont encore des programmes actifs (noms de processus). Le web affiche alors une confirmation ciblée ; l'hôte n'arrête rien tant que le web n'envoie pas `terminal.close` ou `window.close`. `app.closing` porte directement cette activité pour tous les panes vivants.
- L'environnement transmis au shell ajoute `DOCK_TERMINAL=1`, `DOCK_PANE_ID` et `TERM_PROGRAM=DockTerminal`, et retire toute variable `WEZTERM_*`.
- États des agents : l'hôte purge `agents\*.json` au démarrage, à chaque `terminal.create` et `terminal.close` (aucun état ancien n'est restauré comme vivant), puis évalue `AgentMonitor.Resolve(_terminals.Probes())` hors du thread UI toutes les 2 s et au plus 150 ms après un changement du dossier `agents` (`FileSystemWatcher`, changements rapprochés regroupés en une seule évaluation). Il envoie `agent.states {panes[{paneId, agent, state, message?}]}` seulement quand le résultat change ; un pane absent de la liste n'a aucun agent. Le script `hooks\dock-agent-state.ps1`, copié à côté de `Dock.exe`, est le producteur Claude Code : appelé par les hooks `SessionStart` (inconnu), `UserPromptSubmit` et `PostToolUse` (en cours), `PreToolUse` limité par `matcher` à `AskUserQuestion`, `PermissionRequest` et `Notification` de type `permission_prompt`, `elicitation_dialog` ou `agent_needs_input` (en attente : une réponse est réellement requise ; la notification d'inactivité `idle_prompt` est ignorée pour ne pas confondre attente et fin de tour), `Stop` (terminé), `StopFailure` (en erreur), `SessionEnd` (suppression du fichier), il lit `DOCK_PANE_ID` hérité du shell et écrit le fichier du pane ; les messages sont des libellés français fixes (jamais le texte anglais de Claude), une notification d'attente n'écrase pas une attente déjà signalée par `PermissionRequest`, et le script porte un BOM UTF-8 pour que Windows PowerShell 5.1 lise ses accents. `ClaudeHooksInstaller` (`Status`, `Install`, `Remove`) fusionne ou retire ces hooks dans `%USERPROFILE%\.claude\settings.json` uniquement sur `agents.installHooks` / `agents.removeHooks` (clic explicite dans Paramètres) : les autres clés et les hooks étrangers sont conservés, un groupe Dock est reconnu par le chemin de `dock-agent-state.ps1`, l'écriture est atomique ; un fichier illisible remonte en `error` sans être touché (ses commentaires JSON éventuels ne survivent pas à une réécriture). Chaque opération répond par un `settings.result` à jour. Codex CLI n'a pas de producteur : « Inconnu » seulement.
- Ne jamais réimplémenter `wtr` / `rmwt` : ils viennent du profil chargé par PowerShell.
- Contrat de synchronisation worktrees : l'hôte n'exécute aucun effet de `wtr` / `rmwt`. Après `wtr`, le prompt du pane émet OSC 7 avec le nouveau dossier (`terminal.cwd`), rien d'autre. Après `rmwt`, à chaque `terminal.cwd` reçu de n'importe quel pane, `TerminalManager.MissingDirectories` vérifie le dossier courant de toutes les sessions vivantes et l'hôte envoie `terminal.pathMissing {pane, path, fallback}` pour celles dont le dossier a disparu ; même message à `terminal.create` si le dossier demandé n'existe plus (le shell démarre alors dans le dossier utilisateur). Aucun pane ni workspace n'est fermé ou créé automatiquement.
- Un échec de `terminal.create` remonte en `error` avec le `pane` concerné ; le web affiche alors un état local au pane (relance, choix d'un autre shell, fermeture).

## Dock.Host

| Fichier | Rôle |
| --- | --- |
| `App.xaml.cs` | Fixe le dossier de données `%LOCALAPPDATA%\Dock` (remplacé par la variable `DOCK_DATA_DIR` quand elle est définie) et le dossier utilisateur WebView2 qu'il contient. |
| `MainWindow.xaml(.cs)` | Fenêtre ouverte maximisée (taille restaurée 1480 × 900), une `WebView2` qui l'occupe entièrement, aucun `KeyboardAccelerator`. Désactive les raccourcis navigateur, mappe `https://dock.app/` sur `wwwroot/`, ou navigue vers `DOCK_WEB_DEV_URL` si la variable est définie (serveur Vite). À la fermeture par la fenêtre, annule une première fois (`Handled`) et laisse `HostBridge.RequestClose` envoyer `app.closing {activity}` au web ; la fermeture réelle vient de `window.close` renvoyé par le web (après envoi de la disposition et du texte) ou d'un délai de garde de 3 s. Quand des programmes sont actifs, le web envoie `window.closeCancel`, ce qui désarme le délai de garde le temps de la confirmation ; un second clic sur la croix pendant l'attente est ignoré. |
| `Bridge/HostBridge.cs` | Reçoit les messages JSON du web (`WebMessageReceived`), route par `type`, renvoie par `PostWebMessageAsJson`. Regroupe la sortie des terminaux par pane et la vide sur le thread UI en une seule passe. Le thread UI, par lequel passent chaque frappe et son écho, ne fait ni écriture disque ni lecture lente : `session.save` et `text.save` partent dans une file d'écriture en arrière-plan qui préserve l'ordre et qui est vidée avant la fermeture (10 s au plus), `context.query` et `projects.list` dans une seconde file ; une exception dans l'une de ces files remonte en `error`. |
| `Bridge/BackgroundQueue.cs` | File de travaux exécutés un par un, dans l'ordre, sur le pool de threads ; `Drain` attend la fin des travaux en cours. |
| `Bridge/PaneOutputBuffer.cs` | Tampon par pane avec décodage UTF-8 incrémental et contre-pression (le thread de lecture s'arrête au-delà de 4 Mc non acquittés). |
| `Bridge/BridgeCommandModel.cs` | Forme des messages entrants. |
| `Assets/Dock.ico`, `Assets/Dock.png` | Icône de l'application (tuile sombre, chevron de prompt et curseur verts), versionnée : `.ico` multi-tailles 16 → 256 px en PNG, source 256 px. Régénérée par `node scripts/generate-icon.js` (Node seul, aucune dépendance), jamais pendant le build. `<ApplicationIcon>` l'embarque dans `Dock.exe` (Explorateur, barre des tâches, Alt + Tab, raccourcis de l'installeur) ; copiée dans la sortie, elle est appliquée à la barre de titre par `AppWindow.SetIcon` et reste disponible pour les notifications Windows. `web/public/favicon.svg` reprend le même dessin. |
| `hooks/dock-agent-state.ps1` | Script PowerShell livré avec l'hôte (`CopyToOutputDirectory`) que les hooks Claude Code exécutent pour écrire l'état du pane courant dans le sous-dossier `agents` du dossier de données (`DOCK_DATA_DIR` hérité du shell s'il est défini) ; sans `DOCK_PANE_ID` il ne fait rien. |
| `Bridge/AgentStateFeed.cs` | Purge `agents\*.json` au démarrage, surveille ce dossier (`FileSystemWatcher`) et interroge `AgentMonitor` sur un minuteur d'arrière-plan non réentrant (toutes les 2 s, avancé à 150 ms après un changement du dossier), jamais sur le thread UI ; envoie `agent.states` seulement quand le résultat change ; `Forget(paneId)` supprime l'état d'un pane fermé ou relancé ; `Hooks` expose le `ClaudeHooksInstaller` et `Describe` l'état des hooks pour `settings.result`. |
| `Bridge/AttentionNotifier.cs` | Notifications hors focus : `Register` inscrit l'application non empaquetée auprès de `AppNotificationManager` ; `Notify(pane, titre, corps, réglages, force)` ne fait rien quand la fenêtre est active (sauf test), fait clignoter la barre des tâches (`FlashWindowEx`, jusqu'au retour au premier plan) puis joue le son configuré (`PlaySound` avec alias système ou fichier `.wav`, sans dépendance au SDK ; un fichier `.wav` est toujours joué par `PlaySound`, la notification Windows est alors muette) et affiche une notification Windows si l'inscription a réussi (le son passe alors par la notification, `ms-winsoundevent:`) ; cliquer la notification ramène Dock au premier plan et envoie `agent.join {pane}` au web. Limite connue : en déploiement autonome, `AppNotificationManager.Register` échoue avec le Windows App SDK 2.5.1 (issue microsoft/WindowsAppSDK#6774, DLL `Microsoft.WindowsAppRuntime.Insights.Resource.dll` absente) ; l'échec est mémorisé, `settings.result` porte `notifications{toastAvailable, toastError}` et seuls le clignotement et le son sont actifs jusqu'à une version corrigée du SDK. `MainWindow` transmet l'état d'activation via `SetWindowActive`. |
| `Bridge/PathPicker.cs` | Sélecteurs natifs initialisés avec le handle de la fenêtre : fichier exécutable (`.exe`, `.cmd`, `.bat`, tout) ou dossier pour les champs de chemin, fichier `.json` à ouvrir et fichier `.json` à enregistrer (`FileSavePicker`) pour l'import / export des préférences, fichier `.wav` (`target: sound`) pour le son des notifications. Annulation = aucun message. |

## Construction

- `dotnet build Dock.slnx` construit tout. La cible `BuildWeb` de `Dock.Host.csproj` lance `pnpm install` et `pnpm build` si `web/dist/index.html` est absent ou en configuration Release, puis `CopyWebToOutput` copie `web/dist` dans `wwwroot/` du dossier de sortie.
- Publication autonome : `dotnet publish src/Dock.Host/Dock.Host.csproj -c Release -r win-x64 -p:Platform=x64 --self-contained -o publish`. `EnableMsixTooling` est requis pour que le `.pri` soit publié.
- Installeur : `scripts/build-installer.cmd` lit la version de `Dock.Host.csproj`, publie dans `publish/`, télécharge le programme d'installation WebView2 Evergreen puis compile `installer/Dock.iss` avec Inno Setup 6 vers `installer/output/Dock-<version>-setup.exe`. Installation par utilisateur sans droits administrateur (`%LOCALAPPDATA%\Programs\Dock`, élévation proposée en option), WebView2 installé seulement s'il manque, raccourci dans le menu Démarrer et raccourci Bureau optionnel. À la désinstallation, `Dock.exe --remove-claude-hooks` retire les hooks Dock de `settings.json` de Claude Code s'il y en a (`ClaudeHooksInstaller.RemoveIfPresent`, fichier non réécrit sinon), puis une question propose de supprimer `%LOCALAPPDATA%\Dock` (non par défaut, conservé en désinstallation silencieuse). L'installeur n'est pas signé : SmartScreen avertit au premier lancement.
- Release : monter `<Version>` dans `Dock.Host.csproj`, lancer le script, puis `gh release create v<version> installer/output/Dock-<version>-setup.exe --generate-notes`.
- Développement web à chaud : `pnpm dev` dans `web/`, puis lancer l'hôte avec `DOCK_WEB_DEV_URL=http://localhost:5173`.
- Instance isolée : `DOCK_DATA_DIR=<chemin absolu>` fait lire et écrire session, texte, réglages, états d'agents et profil WebView2 dans ce dossier. Indispensable pour lancer une version de développement pendant qu'un Dock installé tourne, sans écraser sa session.

## Conventions

- Messages d'erreur en français, suffixe `Model` pour les classes de données, suffixe `Async` pour les méthodes asynchrones, aucun commentaire dans le code, fichiers de moins de 400 lignes.
- Les erreurs attendues du pont remontent en `error` au web ; les exceptions inattendues ne doivent pas faire tomber l'hôte.
